## 2. Key Findings By Topic

### AGENTS.md convention

`AGENTS.md` is now a cross-agent convention, not only an OpenAI/Codex file. The AGENTS.md site calls it a README for agents and says it should contain build steps, tests, conventions, and other agent-specific context that would clutter a human README ([AGENTS.md](https://agents.md/), no listed date, accessed 2026-06-05). It also says there are no required fields: standard Markdown is enough ([AGENTS.md](https://agents.md/), no listed date).

OpenAI Codex reads `AGENTS.md` before work, builds an instruction chain from global and project scopes, walks from project root to the current directory, and lets closer files override earlier guidance because they appear later in the combined prompt. Codex also has a default combined project-doc size limit of 32 KiB via `project_doc_max_bytes` ([Custom instructions with AGENTS.md](https://developers.openai.com/codex/guides/agents-md.md), fetched 2026-06-05).

The current prompt's `AGENTS.md` canonical entrypoint pattern is directionally aligned. The main gap is monorepo/nested behavior: AGENTS.md explicitly recommends nested `AGENTS.md` for large monorepos, and Codex/GitHub Copilot now support nearest/nested behavior; Cursor's docs still describe root-only `AGENTS.md` in v1.5 with nested support planned ([AGENTS.md](https://agents.md/), [Custom instructions with AGENTS.md](https://developers.openai.com/codex/guides/agents-md.md), [Adding repository custom instructions for GitHub Copilot](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/add-custom-instructions/add-repository-instructions), [Cursor Rules](https://docs.cursor.com/context/rules-for-ai)).

### What belongs in AGENTS.md vs elsewhere

Common consensus: root `AGENTS.md` or equivalent always-on files should contain durable, broadly applicable instructions: project overview, setup/build/test commands, code style, security considerations, repo structure, and workflow expectations ([AGENTS.md](https://agents.md/), [GitHub Copilot response customization](https://docs.github.com/en/copilot/concepts/prompting/response-customization), [VS Code custom instructions](https://code.visualstudio.com/docs/agent-customization/custom-instructions), [Anthropic CLAUDE.md blog](https://claude.com/blog/using-claude-md-files)).

Consensus also says not to overload the always-on file. Anthropic says specific, concise, well-structured instructions work best and gives a target under 200 lines per `CLAUDE.md` ([How Claude remembers your project](https://code.claude.com/docs/en/memory), accessed 2026-06-05). GitHub says Copilot instructions are sent with every chat message and should be short, self-contained, and broadly applicable ([About customizing GitHub Copilot responses](https://docs.github.com/en/copilot/concepts/prompting/response-customization), accessed 2026-06-05). Drew Breunig's context-engineering guidance argues every token in context influences behavior, so irrelevant context causes confusion or conflict ([Working with Contexts](https://www.oreilly.com/radar/working-with-contexts/), 2025-08-28).

Prompt 1's router/progressive-disclosure design is compatible with this, but its absolute `README.md` prohibition is stricter than the sources. The AGENTS.md site distinguishes README for humans from AGENTS for agents, but does not say agents must never read README; GitHub's Copilot onboarding prompt explicitly tells agents to inspect docs and document commands to reduce exploration ([AGENTS.md](https://agents.md/), [Adding repository custom instructions for GitHub Copilot](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/add-custom-instructions/add-repository-instructions)).

### Per-harness files: thin shim vs native guidance

There is no universal consensus that every harness-specific file should be a thin shim.

Claude Code: `CLAUDE.md` is the file Claude reads automatically, not `AGENTS.md`. Anthropic's docs explicitly say that if a repository already uses `AGENTS.md`, create a `CLAUDE.md` that imports it with `@AGENTS.md`, then optionally add Claude-specific instructions below; a symlink also works where practical ([How Claude remembers your project](https://code.claude.com/docs/en/memory), accessed 2026-06-05). A plain "read AGENTS.md" pointer is weaker than Anthropic's recommended import because Claude may not automatically load `AGENTS.md`.

Cursor: Cursor supports project rules in `.cursor/rules/*.mdc`, user rules, `AGENTS.md`, and legacy `.cursorrules`; it says `AGENTS.md` is a simple alternative to `.cursor/rules` for straightforward use cases, while project rules support metadata/scoping. `.cursorrules` is deprecated ([Cursor Rules](https://docs.cursor.com/context/rules-for-ai), no listed date). Therefore, a Cursor shim is optional for simple cross-agent scaffolding; `.cursor/rules` is more justified when you need Cursor-specific or scoped rules.

GitHub Copilot: Copilot now supports repository-wide `.github/copilot-instructions.md`, path-specific `.github/instructions/**/*.instructions.md`, and agent instructions in `AGENTS.md`. GitHub says nearest `AGENTS.md` can take precedence for Copilot agent work, while Copilot's instruction precedence page places path-specific instructions, repository-wide `.github/copilot-instructions.md`, and then agent instructions under repository custom instructions ([Adding repository custom instructions for GitHub Copilot](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/add-custom-instructions/add-repository-instructions), [About customizing GitHub Copilot responses](https://docs.github.com/en/copilot/concepts/prompting/response-customization)). VS Code recommends starting with `.github/copilot-instructions.md` for project-wide Copilot standards, adding `.instructions.md` for scoped rules, and using `AGENTS.md` when multiple AI agents share a workspace ([Use custom instructions in VS Code](https://code.visualstudio.com/docs/agent-customization/custom-instructions), search result published 2026-05).

Conflict: prompt 1 says per-harness files should state "AGENTS.md wins on conflict." That is a repo policy, but it is not the actual precedence used by Copilot and VS Code when multiple instruction files apply. To avoid contradictory instructions, prompt 1 should distinguish "canonical source of repo policy" from "tool-specific load/precedence behavior."

### Syncing canonical instructions into harness-specific files

A plain shim that says "read `AGENTS.md`" is not equally effective across harnesses. Claude Code is the clearest case: the official pattern is not a prose pointer but an `@AGENTS.md` import in `CLAUDE.md`, or a symlink where no Claude-specific content is needed ([How Claude remembers your project](https://code.claude.com/docs/en/memory)). Cursor and Copilot now support `AGENTS.md` directly in some surfaces, so extra files may be unnecessary for simple cross-agent repos; however, Copilot still has repository-wide and path-specific instruction files with their own precedence and code-review size behavior, while Cursor project rules require MDC frontmatter and can be scoped ([Cursor Rules](https://docs.cursor.com/context/rules-for-ai), [About customizing GitHub Copilot responses](https://docs.github.com/en/copilot/concepts/prompting/response-customization), [Use custom instructions in VS Code](https://code.visualstudio.com/docs/agent-customization/custom-instructions)).

The best pattern is therefore not "copy the entire root `AGENTS.md` into every harness-specific file" by default. Blind full-file copying creates three risks: stale generated copies, duplicated/conflicting instructions, and tool-specific format/size violations (for example, Copilot code review's first-4,000-character limit and Cursor MDC frontmatter). A sync tool can still be useful, but it should generate tool-specific adapters from the canonical source, not erase each harness's native shape:

- `CLAUDE.md`: generated import adapter starting with `@AGENTS.md`, plus optional Claude-only notes.
- `.github/copilot-instructions.md`: generated short compatibility adapter or Copilot-specific summary, kept under relevant Copilot limits and not claiming false precedence.
- `.cursor/rules/repo.mdc`: generated MDC file with frontmatter and a short pointer/summary only when Cursor-specific rules are needed.
- Optional validation: fail CI or a local check when generated adapters drift from their source template.

Implication for prompt 1: add an optional scaffolded sync/check script only when the repo wants generated adapters. The script should be described as an adapter generator and drift checker, not as a mandatory whole-file copier. A POSIX shell script is fine when the repo approves shell tooling; otherwise use the repo's existing task runner.

### Progressive disclosure, router entrypoints, and context engineering

The field strongly supports progressive disclosure. OpenAI Codex skills use progressive disclosure: Codex starts with a bounded list of skill names/descriptions/paths and loads a full `SKILL.md` only when selected; the initial list is capped around 2% of context or 8,000 characters when the context window is unknown ([Agent Skills](https://developers.openai.com/codex/skills.md), fetched 2026-06-05).

Claude's `.claude/rules/` can scope rules to path patterns and says task-specific instructions that do not need to be in context all the time should use skills instead, which load only when invoked or relevant ([How Claude remembers your project](https://code.claude.com/docs/en/memory), accessed 2026-06-05). GitHub/VS Code `.instructions.md` files can use `applyTo` patterns and semantic descriptions for file-based application ([Use custom instructions in VS Code](https://code.visualstudio.com/docs/agent-customization/custom-instructions)).

Drew Breunig's context-engineering taxonomy gives the rationale: long contexts can become poisoned, distracting, confusing, or conflicting; mitigations include retrieval, tool loadouts, context quarantine, pruning, summarization, and offloading ([Working with Contexts](https://www.oreilly.com/radar/working-with-contexts/), 2025-08-28). Simon Willison independently emphasizes that managing context to fit limits is critical and subagents preserve root context for larger tasks ([Subagents](https://simonwillison.net/guides/agentic-engineering-patterns/subagents/), 2026-03-17).

Prompt 1's `AGENTS.md` router and `docs/AGENT_TASK_ROUTER.md` are well aligned with this consensus, though the prompt should add native scoped mechanisms for harnesses that support them.

### Context/token minimization techniques

Sources agree on keeping always-on instructions concise, relevant, and non-conflicting. Claude docs: shorter `CLAUDE.md` files produce better adherence and target under 200 lines; comments are stripped before context injection in `CLAUDE.md`, which can save tokens for maintainer notes ([How Claude remembers your project](https://code.claude.com/docs/en/memory)). GitHub: Copilot custom instructions should be short/self-contained and broadly applicable because they are sent with every chat message; Copilot code review reads only the first 4,000 characters of any custom instruction file ([About customizing GitHub Copilot responses](https://docs.github.com/en/copilot/concepts/prompting/response-customization)). Codex: project instructions are capped by default at 32 KiB and nested splitting is a recommended remedy when truncated ([Custom instructions with AGENTS.md](https://developers.openai.com/codex/guides/agents-md.md)).

Practitioner guidance adds that context is not free: irrelevant or conflicting context can degrade model behavior even when the model has space for it ([Working with Contexts](https://www.oreilly.com/radar/working-with-contexts/), 2025-08-28). Simon Willison notes code execution and verification matter because coding agents can iterate until the code demonstrably works ([Agentic manual testing](https://simonwillison.net/guides/agentic-engineering-patterns/agentic-manual-testing/), 2026-03-06).

Prompt 1's token-minimization rules are strong, but should add tool-specific size constraints and say line caps are local house targets, not universal standards.

### Long-running harness state and session protocol

The additional harness-engineering sources sharpen the distinction between a repo instruction scaffold and a long-running agent harness. OpenAI's Codex case study says the team tried "one big `AGENTS.md`" and rejected it because it crowded out task/code context, made all guidance feel equally important, rotted quickly, and was hard to verify. Their replacement was a roughly 100-line `AGENTS.md` as a table of contents, with a structured `docs/` knowledge base as the system of record, including indexed design docs, active/completed execution plans, generated references, quality docs, and recurring doc-gardening automation ([Harness engineering](https://openai.com/index/harness-engineering/), 2026-02-11).

Anthropic's long-running-agent harness adds concrete state handoff artifacts: an initializer agent creates an `init.sh`, a progress file, a feature list, and an initial commit; later coding agents read progress, git history, and the feature list, choose one unfinished feature, verify baseline functionality, implement incrementally, and leave the repo in a clean state ([Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents), 2025-11-26). Anthropic reports that JSON worked better than Markdown for the feature list because models were less likely to rewrite or corrupt it, and that coding agents should only flip pass/fail state rather than remove or rewrite tests/features.

Geoffrey Huntley's Ralph pattern independently argues for one item per loop, keeping the primary context window as a scheduler, using subagents for expensive search/summary work, limiting validation parallelism to avoid backpressure, and explicitly warning the agent not to assume code is missing before searching ([Ralph Wiggum as a "software engineer"](https://ghuntley.com/ralph/), approx. 2025-07). The community best-practices synthesis echoes these ideas: orient, setup, verify baseline, select one task, implement, test through UI/API, update state, and clean exit ([Best Practices for Building an Agent Harness](https://github.com/celesteanders/harness/blob/main/docs/best-practices.md), no listed date).

Implication for prompt 1: keep the lean initial markdown scaffold as default, but add an optional "long-running autonomous harness" profile that can include non-markdown state files (`feature_list.json`), executable setup scripts (`init.sh`), active progress notes, and explicit session lifecycle rules. This conflicts with prompt 1's current tendency to avoid non-markdown scaffolding unless approved, so it should be gated by interview answers.

### Evaluator loops, backpressure, and mechanical enforcement

OpenAI's Codex case study emphasizes making the application legible to agents: bootable per worktree, browser automation through Chrome DevTools, screenshots and DOM snapshots, and local logs/metrics/traces queryable through standard APIs. It also says documentation alone did not keep the codebase coherent; architecture and taste were enforced mechanically through custom linters, structural tests, file-size rules, and lint messages that included remediation instructions ([Harness engineering](https://openai.com/index/harness-engineering/), 2026-02-11).

Anthropic's March 2026 harness-design post adds a planner-generator-evaluator architecture. It says agents are over-generous when grading their own work, especially on subjective tasks, and that a separate skeptical evaluator is easier to tune. The evaluator used concrete grading criteria, few-shot calibration, Playwright MCP, screenshots, and iterative critique; the same generator-evaluator loop maps to full-stack development through code review and QA ([Harness design for long-running application development](https://www.anthropic.com/engineering/harness-design-long-running-apps), 2026-03-24). The post also warns that harnesses should be re-examined after model upgrades: remove pieces that are no longer load-bearing and add pieces that unlock newly possible capabilities.

Implication for prompt 1: the scaffold should not only say "run tests"; it should capture fast feedback loops and the agent-visible verification surface. For UI/web apps, the interview should ask whether browser automation, screenshots, logs, metrics, traces, or worktree-isolated app instances are available or desired. For complex work, it should optionally define a QA/evaluator loop and sprint contract: what will be built, how it will be graded, and what threshold counts as done.

### Stable standard/decision IDs vs prose

No primary source found requires stable standard IDs like `S-PLAN-001`. The closest support is indirect: official docs and practitioners recommend concise, specific, reusable instructions; stable IDs are a local mechanism for reducing repetition and making plans/final summaries refer to durable rules ([GitHub Copilot response customization](https://docs.github.com/en/copilot/concepts/prompting/response-customization), [Working with Contexts](https://www.oreilly.com/radar/working-with-contexts/)).

Recommendation: keep stable IDs as a local optimization, but label them as project scaffolding convention rather than ecosystem best practice. Confidence is medium because there is no direct source agreement.

### Nested / monorepo AGENTS.md

AGENTS.md says large monorepos should place another `AGENTS.md` inside each package; closest file wins, and explicit user prompts override everything ([AGENTS.md](https://agents.md/), no listed date). Codex walks from project root to current directory and concatenates one instruction file per directory, with closer files later in the prompt and therefore overriding earlier guidance ([Custom instructions with AGENTS.md](https://developers.openai.com/codex/guides/agents-md.md)). GitHub Copilot docs say one or more `AGENTS.md` files can be stored anywhere in the repository and the nearest takes precedence when Copilot is working ([Adding repository custom instructions for GitHub Copilot](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/add-custom-instructions/add-repository-instructions)). VS Code nested `AGENTS.md` support is experimental via `chat.useNestedAgentsMdFiles` ([Use custom instructions in VS Code](https://code.visualstudio.com/docs/agent-customization/custom-instructions)). Cursor currently says root-level only for `AGENTS.md` and no scoping, with nested support planned for v1.6 ([Cursor Rules](https://docs.cursor.com/context/rules-for-ai)).

Prompt 1 currently generates only root `AGENTS.md`; it should add an optional monorepo phase that creates nested `AGENTS.md` only when subproject boundaries are known.

### Emerging patterns: skills, memories, rules, and custom agents

OpenAI Codex skills use `SKILL.md` plus optional scripts/references for reusable workflows; repo-scoped skills live under `.agents/skills` and are discovered progressively ([Agent Skills](https://developers.openai.com/codex/skills.md)). Claude Code docs direct task-specific instructions to skills and path-specific durable instructions to `.claude/rules/` ([How Claude remembers your project](https://code.claude.com/docs/en/memory)). VS Code/Copilot supports file-based `.instructions.md` and custom agents, while GitHub added `excludeAgent` to target Copilot code review vs coding agent in `.instructions.md` frontmatter ([Use custom instructions in VS Code](https://code.visualstudio.com/docs/agent-customization/custom-instructions), [Copilot code review and coding agent now support agent-specific instructions](https://github.blog/changelog/2025-11-12-copilot-code-review-and-coding-agent-now-support-agent-specific-instructions/)).

Memory files are not a replacement for checked-in repo rules. Codex says required team guidance belongs in `AGENTS.md` or checked-in documentation; memories are local recall, not the only source for rules that must apply ([Memories](https://developers.openai.com/codex/memories.md)). Claude's auto memory stores discovered learnings locally and loads an entrypoint with a 200-line/25KB limit; `CLAUDE.md` remains the human-written team instruction surface ([How Claude remembers your project](https://code.claude.com/docs/en/memory)).

Prompt 1 should not automatically scaffold all of these, but should ask whether advanced harness surfaces are desired when the user names those tools.

For skill files, the same adapter rule applies. There is no evidence from the consulted sources for a universal `SKILLs.md` file that should be copied wholesale to every harness. Codex's primary repo-scoped skill shape is `.agents/skills/<name>/SKILL.md` with optional scripts/references, and Codex uses progressive disclosure over skill descriptions before loading full skill instructions ([Agent Skills](https://developers.openai.com/codex/skills.md)). Other harnesses may have custom agents, commands, or rules with different metadata and invocation semantics. If a repo wants cross-harness skills, use one canonical skill source plus a sync/export tool that generates harness-specific adapters while preserving each target's required frontmatter, descriptions, paths, and size constraints. Do not copy large skill bodies into always-on instruction files; that defeats progressive disclosure.

### Recommended file size / line-count targets

There is no universal line-count target for all agent files. Specific targets found:

- Claude: target under 200 lines per `CLAUDE.md`; shorter files produce better adherence ([How Claude remembers your project](https://code.claude.com/docs/en/memory)).
- GitHub Copilot code review: only first 4,000 characters of any custom instruction file affect code review ([About customizing GitHub Copilot responses](https://docs.github.com/en/copilot/concepts/prompting/response-customization)).
- GitHub Copilot onboarding prompt: generated instructions must be no longer than two pages and not task-specific ([Adding repository custom instructions for GitHub Copilot](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/add-custom-instructions/add-repository-instructions)).
- Codex: default combined project docs limit is 32 KiB via `project_doc_max_bytes`; split across nested directories or raise the limit if truncated ([Custom instructions with AGENTS.md](https://developers.openai.com/codex/guides/agents-md.md)).

Prompt 1's `AGENTS.md <= 80 lines`, router <= 120, and standards <= 200 are local optimization constraints. They are stricter than official docs but consistent with context minimization if treated as soft targets with approval gates.

### Anti-patterns warned against

Common anti-patterns:

- Overloading always-on context with irrelevant details; Breunig calls out context distraction/confusion/clash and says every token influences behavior ([Working with Contexts](https://www.oreilly.com/radar/working-with-contexts/)).
- Creating contradictory instructions; Claude docs warn contradictory rules may be selected arbitrarily and recommend periodic review ([How Claude remembers your project](https://code.claude.com/docs/en/memory)).
- Treating markdown instructions as enforcement. Claude says settings are enforced by the client while `CLAUDE.md` only shapes behavior; Codex rules similarly control command approvals outside markdown ([How Claude remembers your project](https://code.claude.com/docs/en/memory), [Rules](https://developers.openai.com/codex/rules.md)).
- Adding theoretical "best practices" that do not match actual workflow; Anthropic says effective `CLAUDE.md` files solve real problems and reflect how the team actually develops software ([Using CLAUDE.md files](https://claude.com/blog/using-claude-md-files)).
- Relying on unverified generated code; Willison says never assume LLM-generated code works until executed ([Agentic manual testing](https://simonwillison.net/guides/agentic-engineering-patterns/agentic-manual-testing/)).
- One-shotting large app builds or declaring work done prematurely. Anthropic observed both failure modes and mitigated them with initializer/coding-agent separation, a feature list, one-feature-at-a-time work, progress notes, and baseline end-to-end verification ([Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents), 2025-11-26).
- Expecting agents to judge their own output objectively. Anthropic found a separate skeptical evaluator/QA loop easier to tune than making the generator self-critical ([Harness design for long-running application development](https://www.anthropic.com/engineering/harness-design-long-running-apps), 2026-03-24).
- Letting docs and architectural rules drift without mechanical checks. OpenAI reports that documentation alone was insufficient and promoted durable taste/architecture rules into linters, structural tests, recurring doc-gardening, and cleanup tasks ([Harness engineering](https://openai.com/index/harness-engineering/), 2026-02-11).

Prompt 1 already covers many of these, but should add explicit conflict/staleness review and "markdown is not enforcement" language.

## 5. Open Questions

- There is no settled cross-agent standard for path-scoped instructions. Claude uses `.claude/rules/` with `paths`, Cursor uses `.cursor/rules/*.mdc` with `globs`/`alwaysApply`, Copilot/VS Code uses `.github/instructions/*.instructions.md` with `applyTo`, and `AGENTS.md` nested support varies by tool.
- There is no consensus that `AGENTS.md` should be a tiny router rather than a fuller onboarding file. Official examples include setup commands, testing instructions, and PR rules directly in `AGENTS.md`; prompt 1's router pattern is a deliberate context-minimization strategy rather than the only recommended pattern.
- Stable IDs for standards and decisions are a plausible compression mechanism, but not a published ecosystem convention in the sources consulted.

- Memory systems are evolving quickly. Current guidance says memories are useful local recall but checked-in repo guidance remains the durable team control surface.
- Long-running harness architecture is task- and model-dependent. Anthropic reports context resets were essential for one model/harness but later compaction was sufficient for a stronger model; prompt 1 should avoid hard-coding one orchestration strategy.
- It is unresolved how much of OpenAI's high-autonomy Codex workflow generalizes to ordinary repos without similar investment in local tooling, observability, custom lints, doc-gardening, and agent review loops.
- There is no consensus on when to add multi-agent orchestration. Anthropic shows planner/generator/evaluator can help for hard long-running tasks; the community synthesis warns multi-agent systems add microservice-like complexity and should be added only after a specific single-agent ceiling is observed.
- There is no published consensus that a bash script should copy root `AGENTS.md` or `SKILL.md` files wholesale into harness-specific locations. The safer synthesis is canonical source plus generated adapters/drift checks, with whole-file copy used only for a target that lacks import/support and can tolerate the size/format.
